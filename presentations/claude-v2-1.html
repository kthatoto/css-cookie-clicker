STEP 1

checkbox 1個 ＝ クリック1回分の記憶

このゲームに変数はありません。あるのは checked か unchecked かの2状態だけ。
左の 🍪 は <label>、右のチェックボックスが <input type="checkbox"> 本体です。同じ1個の要素なので、cookie を押すと本物のチェックが入ります。

unchecked
まだ押されていない
checked
1回押した、という事実だけが残る

押しても「1回押された」以上のことは記録されません。何枚もらえるかは、このあと CSS 側が決めます。

STEP 2

同じ場所に重ねると「連続クリック」になる

本物は同じ座標に 100個重なっています。DOM順で後ろの要素ほど手前に描かれるので、押せるのはいつも一番手前の1個だけ。押されたものは脇へ飛び、次が手前に出てきます。

↑ これが本物の <input type="checkbox"> 6個。右端から順にチェックが入っていきます。

z-index も JavaScript も使っていません。「後に書いた要素が手前」という既定の規則だけです。

STEP 6

同じ残高でも、押し方ごとに別のCSSが要る

下はどれも 合計10枚になる押し方です。ところが CSS から見ると、これらはまったく別の状態。
「10枚あるか」を計算する手段がないので、押し方の組み合わせごとにセレクタを1本ずつ用意してあります。

/* rate-1 を10回。rate-2 は0回 */
#main:has(#item1:checked):has(#item2:not(:checked))
     :has(> .click-group.rate-1 > input:nth-last-child(10):checked)
  .item2 .purchase { --purchase-background: skyblue; }
/* rate-1 を8回、rate-2 を1回 */
#main:has(#item1:checked):has(#item2:not(:checked))
     :has(> .click-group.rate-1 > input:nth-last-child(8):checked)
     :has(> .click-group.rate-2 > input:nth-last-child(1):checked)
  .item2 .purchase { --purchase-background: skyblue; }
/* rate-1 を6回、rate-2 を2回 */
#main:has(#item1:checked):has(#item2:not(:checked))
     :has(> .click-group.rate-1 > input:nth-last-child(6):checked)
     :has(> .click-group.rate-2 > input:nth-last-child(2):checked)
  .item2 .purchase { --purchase-background: skyblue; }
/* rate-1 を2回、rate-2 を4回 */
#main:has(#item1:checked):has(#item2:not(:checked))
     :has(> .click-group.rate-1 > input:nth-last-child(2):checked)
     :has(> .click-group.rate-2 > input:nth-last-child(4):checked)
  .item2 .purchase { --purchase-background: skyblue; }

タブを切り替えると、生成されているCSSも丸ごと別物になります。これが「アイテムを1個増やすのが高くつく」正体です。

STEP 7

状態 ＝ 購入済みアイテムの集合

好きな順に押してみてください。順番は関係ありません。どの組み合わせでも、必ず対応する1つの状態に落ちます。

0000100001000010 0001110010101001 0110010100111110 1101101101111111

今ハイライトされている1つを選ぶために、16通りぶんのセレクタがこのスライドにも手で書いてあります。 本物のゲームでは、この16通りそれぞれについて、さらに STEP 6 の押し方の組み合わせが掛け算されます。

8 / 11
STEP 8 ／ ネタバラシ

CSSは計算していない。全部あらかじめ書いてある

手続き的（JavaScript なら）

// 状態は変数。押されたら「計算して」求める
let cookies = 0, rate = 1;

onClick  = () => cookies += rate;
onBuy    = (item) => {
  cookies -= item.price;
  rate += 1;
};

この数行で、あらゆる残高・あらゆる購入状況に対応できる。実行時に計算するから。

宣言的（このゲームのCSS）

/* 「この状態のときは、こう見える」を並べるだけ */
#main:has(#item1:checked)
     :has(> .rate-1 > input:nth-last-child(6):checked)
     :has(> .rate-2 > input:nth-last-child(2):checked)
  .item2 .purchase { background: skyblue; }

/* ↑ これが、起こりうる状態の数だけ並んでいる */

CSSに「足す」も「比べる」もない。あるのは「この形に当てはまるか」だけ。

だから残高は「増えていく数」ではなく、今この瞬間の checked の並びから、毎回そのまま読み出されている結果にすぎません。
そして、いま見ているこの資料のページ送りも同じ仕掛けです。#st9:checked ~ .stage .sl9 { opacity: 1 } を、スライドの数だけ並べてあります。

STEP 9

だから Sass で「総当たり」して吐き出す

手で書ける量ではないので、購入済みの集合×各rate群の押した回数を再帰的に全列挙し、購入可能になる境界だけにルールを生成しています。

1個2通りの状態
2個4通りの状態
3個8通りの状態
4個16通りの状態
8個256通りの状態

さらに各状態に、STEP 6 で見た「押し方の組み合わせ」が掛かります。 実際このリポジトリの style.css は 24,000行以上に膨らんでいます。

まとめ

まとめ

  • 🍪 checkbox 1個が「1回押した」という記憶。数を持てるのはこれだけ。
  • 📚 同じ場所に100個重ねて、手前から消費させることで連続クリックに見せている。
  • 🔢 残高は counter が数え上げた結果。過去の押した分は、後から単価が変わらない。
  • 🧩 購入可否も rate 切替も、祖先に対する :has() の条件分岐で表現できる。
  • 🧨 CSSは計算しない。起こりうる状態を全部あらかじめ宣言してあるだけ。だからSassで生成する。

この資料自体も JavaScript ゼロ。ページ送りはラジオボタン、キー操作はラジオグループの標準動作、リセットは <input type="reset"> です。
